# 討論結論 1：exec 能不能換成 system()、以及延伸的效能與擴充性

這份文件記錄一場設計討論的結論，不是規格，也不是待辦。內容圍繞
`src/exec.cpp` 是否該改用 `system()`，以及由此延伸出的效能、巢狀擴充、
串流讀取等問題。

## 使用情境（討論的前提）

先把 aos-c 的定位釘住，因為所有結論都建立在它上面：

- 核心用法：`aos-c XXX` 讀 `XXX/.aos/insts`，每八行拆成一個 `inst_t`，
  逐個執行。
- insts 檔**由固定函數產出、由 aos-c 讀取**，兩端都是機器，中間沒有
  shell 的角色。八行格式只是目前圖方便的做法，日後可能換別的格式，那是
  技術細節，不影響下面的結論。
- stdin/stdout/stderr 重導向、cwd、env **都是硬性需求**。
- 主要跑在 cron（或類似的定期／背景觸發）之下。
- **不打算併行**：一次跑一個子行程，跑完再跑下一個。
- 放棄 Windows；平台程式碼的清理另外交辦，本次不處理。
- 一個想要的擴充方向：`XXX/.aos/insts` 可以是 pipeline 之類的**串流檔案**
  （FIFO / pipe），aos-c 當長命的串流消費者。

## 結論一：不要改用 system()

`system()` 只是 `fork` + `exec("/bin/sh -c …")` + `waitpid` 的包裝，它把
三步黏死、又硬塞一個 shell 當中間人。對這個專案它做不到硬需求：

- **argv 是陣列，不是字串**。現在用 `execvp(argv[0], argv.data())` 直接傳
  陣列；換 `system()` 得把 argv 拼成字串並做 shell 跳脫，機器資料一旦含
  空白／引號／`$`／`;` 就會被 shell 曲解，等於憑空引入注入面。
- **重導向、cwd、env 沒有乾淨做法**。這三件事現在是在「fork 之後、exec
  之前」的子行程裡做的（`dup2` / `chdir` / 設 `environ`）；`system()` 沒有
  這個縫可以插手，只能改父行程的全域 cwd／environ，那是會互相污染的副
  作用，尤其在「一次跑多個 inst」的迴圈裡。
- **分不清「指令不存在」和「指令跑了回傳 127」**。現在靠 CLOEXEC 管道
  分得清清楚楚；`system()` 兩者都給 127。
- **錯誤分類與訊號語意會退化**。現在 `ExecState` 把各階段失敗分開、訊號
  終止統一成 `128+signal`；`system()` 只有一個依平台而異的回傳碼。

一句話：`system()` 看起來短，但因為做不到硬需求，補回那些能力後只會比
現在更長、更脆。fork/exec 就是這個需求的最小正確解，`exec.cpp` 的執行
邏輯建議原封不動。

## 補充：exec 家族是什麼（給不熟 Linux 的人）

「開一個新程式來跑」在 Linux 上是兩步：

1. `fork()`：把目前行程複製成父子兩個。
2. `exec*()`：在子行程裡把「自己的程式映像」整個換成另一個程式。換成功
   就不再返回；會返回只代表失敗（例如找不到執行檔）。

能在 fork 之後、exec 之前做重導向／chdir／換 env，就是因為卡在這個空檔。
`exec*` 一家人是同一個系統呼叫的各種包裝，後綴決定差別：

- `l` = 參數一個一個列；`v` = 參數放陣列（vector）。
- `p` = 幫你在 `PATH` 裡找執行檔（否則要給完整路徑）。
- `e` = 自帶環境變數陣列。

本專案用 `execvp` = 陣列參數 + PATH 搜尋，正好對上需求。環境變數本來最想
用 `execvpe`（v+p+e），但它是 glibc 專屬、不可攜，所以子行程改成在 exec 前對
`inst.env` 的每一筆呼叫 `setenv`，在繼承的環境上覆寫同名、新增其餘。

## 結論二：效能與生命週期（以目前規模估）

數量級估計（實際隨硬體、檔案系統、page cache 冷熱而變）：

| 步驟 | 時間量級 | 備註 |
|---|---|---|
| 讀 insts + 切八行 | ~10–100 µs | 小檔從 page cache 拿，微秒級 |
| open 三個重導向 + dup2 | ~10–50 µs | |
| chdir | ~1–5 µs | |
| 設 environ | ~1 µs | 只是指標賦值 |
| fork | ~50–300 µs | COW，成本來自複製分頁表而非真記憶體 |
| execvp（含動態連結） | ~1–5 ms | **最貴**，但這是目標程式的啟動成本，不是框架的 |
| waitpid | = 子程式執行時間 | 純等待，本身無開銷 |

- **框架自身開銷 < 1 ms／筆**；真正的時間全在 `execvp` 之後（目標程式自己
  啟動 + 執行），那不是 aos-c 能優化的。
- **記憶體 O(1)**：`run_stream` 一次只留一筆 `inst`（重複用同一組緩衝），
  循序執行 → 同時只有一個子行程。所以不管 insts 有 10 筆還是百萬筆，
  aos-c 用量幾乎不變（RSS 幾 MB，多為 libc/libstdc++ 的共享分頁；私有髒
  記憶體數百 KB 以下）。
- **沒有值得做的微優化**：sub-ms 的開銷對上 execvp + 子程式執行時間是雜訊。
  `posix_spawn` 對這種小父行程零收益又更複雜，別碰。唯一有意義的效能槓桿
  是「循序 vs 併行」——而本專案選擇不併行。

## 結論三：巢狀與規模——深度便宜，寬度才咬人

若 insts 裡又呼叫 aos-c、層層往下：

- 用**循序**執行時，任一時刻活著的行程數 ≈ **巢狀深度**，不是總數。每層
  父 aos-c 都卡在 `waitpid` 等子鏈，幾乎不吃 CPU。
- **深度很便宜**：100 層祖先卡在 waitpid，成本是幾十 MB + 每條路徑的 fd
  問題（見下）。
- **寬度（真正的同時執行數）才是會撞牆的**：記憶體、PID／任務數上限
  （cron／systemd 的 `TasksMax`、容器的 `pids.max` 常只有幾千）、CPU 爭用，
  全綁在「同時幾個」上。
- 因此「總量 10 萬」本身不可怕，可怕的是「同時 1 萬」。而本專案**不併行 +
  串流**，天生把同時量壓在深度上 → 資源是 O(深度) 行程、每個 O(1) 記憶體，
  不會爆。串流巢狀就是一條 Unix 式處理管線。

## 結論四：串流讀取是這個設計的天作之合

- **現在的程式碼已支援**：`read_instruction` 用 `in.get()` 逐字元讀，遇到
  FIFO/pipe 會自然阻塞等資料；`run_stream` 就是「讀一筆→跑一筆→再讀」。
  把 insts 換成 FIFO 或吃 stdin 即可，核心不用改。逐字元讀有 streambuf
  緩衝，不是每字元一個 syscall，效能無虞。
- **序列 + 串流 = 資源永遠有界**：同時一個子行程、記憶體 O(1)，總量再大
  只是跑得久。
- 提醒：`std::ifstream` 開 FIFO 為讀取時，會**阻塞到有寫入端出現**才返回，
  這是 FIFO 的語意，不是當掉。

## 結論五：CLOEXEC 的 fd 洩漏（串流下會變成掛死風險）

這是今天最值得記下來的具體技術點。先解釋 CLOEXEC 是什麼：

- `fork` 會把父行程**所有已開啟的檔案描述符（fd）複製一份給子行程**。
- 子行程接著 `execvp` 換成新程式，但**fd 預設會活過 exec**——新程式因此
  繼承了它根本沒要求開的 fd。
- **CLOEXEC（close-on-exec）** 是掛在 fd 上的一個旗標，意思是「exec 成功時
  自動把這個 fd 關掉」。設了它，fd 就不會漏進被執行的程式。

現在的問題：`run.cpp` 用 `std::ifstream` 開 insts，**這個 fd 沒有 CLOEXEC**。
於是每個子行程都繼承了父 aos-c 的 insts fd，而且 execvp 之後還在。

- **批次檔情境**：只是醜。巢狀 100 層時，最底層被執行的程式會拖著上游
  100 個用不到的 insts fd（和層數成正比），大多無害。
- **串流 / FIFO 情境**：升級成**真實的掛死風險**。串流的 aos-c 是長命行程，
  整條生命握著 FIFO 的**讀端** fd；它 fork 出的子行程繼承了這個讀端、又
  活過 exec。於是任何一個被執行到的長命程式，都握著這條 FIFO 的讀端。
  後果：即使 aos-c 早就結束，上游寫入端仍看到「這條 pipe 還有讀者」，
  **永遠等不到 EOF/EPIPE，可能無限阻塞**。

**修法**：開 insts 時給 fd 設 `O_CLOEXEC`。注意 `std::ifstream` 沒有可攜的
辦法設它，可能得改用 `open()` + `O_CLOEXEC`（或 glibc 的 `fopen("…","re")`）
再包成 stream。

對照之下，`exec.cpp` 對其他 fd 的處理是對的，可作為範本：回報用的 pipe
寫端有設 CLOEXEC（`exec.cpp` 的 `F_SETFD, FD_CLOEXEC`）；重導向 fd 在
`dup2` 到 0/1/2 之後把原 fd 關掉。**唯獨 insts 這條讀取路徑漏了。** 走串流
之前應該先補這一條。

## 結論六：解析失敗時「整條停」的取捨

- 現況：任何一筆解析失敗就印錯並**停止整條串流**（見 `run.cpp` 與 commit
  8f162d8）。理由是八行格式**記錄之間沒有分隔符**，一旦錯位會一路歪下去，
  繼續讀等於執行沒人寫過的指令。這個理由在串流下依然成立——串流不會讓你
  有辦法重新對齊。
- 但後果在串流下變重：長命消費者停了就是**永久死掉**，得靠外部重啟。
- 建議：串流初期維持「錯位即死 + 靠 cron/supervisor 重啟」，別為容錯把格式
  搞複雜。若哪天「串流不可中斷」成為硬需求，才考慮讓格式帶 framing／記錄
  邊界（那樣才可能在錯位後重新同步）——那是明確的格式版本升級，不是縫補。
- 註：八行格式本身是可替換的技術細節，未來換格式時把「能否重新同步」一起
  納入考量即可。

  並加上 `O_NONBLOCK`，開檔不再阻塞（`SPEC_stream_1`）。
