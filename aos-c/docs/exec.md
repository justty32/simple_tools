# 執行行為

一筆指令就是一次「開一個行程」的完整描述。這份文件說明每個欄位在執行時到底做了
什麼、什麼情況算失敗、以及失敗之後會發生什麼。

格式本身（八行怎麼排、Tab 怎麼分）看 [format.md](format.md)。

## 一句話版本

拿到一筆指令之後，會依序做這些事：

1. `fork` 出子行程
2. 在子行程裡：開重導向的檔案、切工作目錄、換環境變數
3. 在子行程裡：`execvp` 換成目標程式
4. 在父行程裡：等子行程結束、把結束狀態寫進檔案

**忠實度對齊 shell。** 第 2、3 步任何一步失敗，子行程就用一個結束碼收場（126 或
127），跟 shell 一樣；對呼叫端而言這筆是「跑完了」，不是這個函式庫壞了。真正會被
回報成錯誤的只剩 `fork` 失敗、等待失敗、exit 檔寫不進去這三種。

## 每個欄位做什麼

### argv：要跑什麼

第一個引數是程式名稱，走 `PATH` 查找 —— 跟你在 shell 裡直接打那個指令的行為一致。
所以 `echo` 找得到，`./my-script` 也找得到（含斜線就不查 `PATH`）。

引數原樣傳給程式，不做任何展開。`*.txt` 就是這五個字元，不會變成一串檔名。

argv 是空的，或第一個引數是空字串，會直接被拒絕（`INVALID_ARGUMENT`），連 `fork`
都不會發生。

### stdin / stdout / stderr：重導向

| 值 | 行為 |
| --- | --- |
| 空 | **繼承**呼叫者的對應控制代碼 |
| 有路徑（stdin） | 以唯讀開啟。開不起來，這筆的結束碼就是 126 |
| 有路徑（stdout/stderr） | 以唯寫開啟，**不存在就建立，存在就清空** |

三個各自獨立，可以只重導向其中一個。

**輸出是截斷不是追加。** 選這個是因為：追加的結果沒辦法由呼叫端還原（內容已經混在
一起了），而截斷可以靠換一個新路徑來避免。等同 shell 的 `>` 而不是 `>>`。如果你
要追加，現在的做法是自己在指令裡用 `sh -c 'cmd >> file'`。

留空是「繼承」而不是「丟到 /dev/null」，因為後者會讓輸出無聲消失，除錯時很痛苦。
真的要丟掉就明確寫 `/dev/null`。

### cwd：工作目錄

留空就繼承呼叫者的工作目錄。有值就在子行程裡 `chdir` 過去，切不過去的話這筆的
結束碼就是 126。

注意順序：**重導向的檔案是在 `chdir` 之前開的**，所以重導向路徑裡的相對路徑是相對
於「呼叫者的」工作目錄，不是 `cwd` 欄位指定的那個。

### env：環境變數

| 值 | 行為 |
| --- | --- |
| 空 | 子行程**完整繼承**呼叫者的環境變數 |
| 有內容 | 用這些變數**取代**整個環境 |

環境變數就寫在第 7 行裡，Tab 分隔：

```text
PATH=/usr/bin:/bin→LANG=zh_TW.UTF-8→EMPTY=
```

**取代，不是擴充。** 這一行只要有內容，呼叫者原本的環境變數一個都不會傳下去 ——
包括 `PATH`、`HOME`、`LANG`。這是刻意的：取代能做出可重現的執行環境，而「擴充」
可以由你自己把要保留的變數寫進去來達成；反過來卻做不到。

如果你的指令需要 `PATH`，記得自己寫一筆。

格式規則（完整版在 [format.md](format.md#env-行一樣只有-tab-有意義)）：

- 每筆是 `KEY=VALUE`，要有 `=`，而且 `=` 不能在最前面
- 值可以是空的，值裡面也可以有 `=`，只有第一個算分隔
- 不做引號處理，不做變數展開 —— 跟 argv 一樣，所有字元都是字面值
- 不合格的一筆是 `ENV_ENTRY_MALFORMED`，在**讀取**階段就被擋下，那筆記錄根本
  不會走到執行

**這一層不整理你的 env。** 不合併、不排序、不去重，原樣交給子行程；重複的鍵誰贏
由 libc 決定。要查、要改單一變數，那是產生指令的人該做的事 —— 它自己有 map，攤平
成幾筆 `KEY=VALUE` 再交過來就好。

### exit：把結束狀態記下來

| 值 | 行為 |
| --- | --- |
| 空 | 結束狀態不記錄，只透過回傳值給你 |
| 有路徑 | 檔案被清空，然後寫入十進位的狀態值加一個換行 |

**有設就一律寫，成敗都寫。** exit 檔是「這一筆做完了」的信號，不是「做對了」的
信號。等著讀這個檔的人，看到它有內容就知道這筆結束了；指令做得對不對，看它的
stdout / stderr。

寫進去的數字是這樣決定的：

| 情況 | 碼 |
| --- | --- |
| 正常結束 | 程式自己的結束碼（0 到 255） |
| 被訊號終止 | `128 + 訊號編號` |
| `execvp` 失敗（找不到指令、沒有執行權限） | 127 |
| exec 前的佈置失敗（重導向開不起來、cwd 切不過去） | 126 |

全部沿用 shell 的慣例。所以被 `SIGTERM`（15）殺掉會記成 `143`，被 `SIGKILL`（9）
殺掉會記成 `137`。這樣做的好處是這個欄位永遠只是一個數字，不需要另一種編碼；壞處
是理論上分不清「被訊號 15 殺掉」和「程式自己 exit(143)」，也分不清「找不到指令」
和「程式自己 exit(127)」。訊號那一項還有救 —— C API 的
`aos_exec_result.signalled` 會告訴你；126/127 那一項則是刻意不救，理由在下面。

### extra：保留

目前完全不使用。留著是為了以後加東西時不用改格式版本。

## 什麼算失敗

這是最需要講清楚的部分。**「子行程回傳非零」不是失敗，「指令根本沒起來」也不是。**

| 情況 | 算什麼 | exit 檔 |
| --- | --- | --- |
| 程式跑完，回傳 0 | 成功 | 寫入 0 |
| 程式跑完，回傳 3 | **成功** | 寫入 3 |
| 程式被訊號殺掉 | **成功** | 寫入 128 + 訊號編號 |
| 找不到指令 | **成功** | 寫入 127 |
| 重導向的檔案開不起來 | **成功** | 寫入 126 |
| cwd 不存在 | **成功** | 寫入 126 |
| `fork` 失敗 | 失敗 | **不會被建立** |
| 等待子行程時出錯 | 失敗 | 同上 |
| exit 檔寫不進去 | 失敗 | 檔案狀態不確定 |

分界線是：**有沒有產出一個結束碼。** 有的話，那個碼就是資料，記進 exit 檔；沒有
的話（`fork` 都失敗了，根本沒有子行程），才是這個函式庫要回報的錯誤。

注意這張表講的是**單一一筆**的成敗判定。失敗之後會不會繼續跑下一筆，是
[多筆指令](#多筆指令)那一節的事 —— 答案是會。

### 為什麼不去分辨「找不到指令」和「指令回傳 127」

技術上做得到：`fork` 之前開一條 `FD_CLOEXEC` 的管道，子行程在 `execvp` 之前失敗
就往裡面寫，`execvp` 成功則管道被自動關閉，父行程讀到 0 個位元組。這條路以前確實
走過。

不走了，理由是它跟這個工具的消費模型對不起來：

- **消費端看的是 exit 檔。** 而分辨出來的「啟動失敗」是個沒有結束碼的狀態，寫不進
  exit 檔 —— 於是「指令沒起來」這筆就永遠不會出現 exit 檔，等著它的人只能一直等。
- **shell 從來不分。** 打錯指令名字的時候 `$?` 就是 127，沒有人因此覺得 shell 少
  講了什麼。指令到底做了什麼，看的是它的 stdout / stderr。
- **少一條管道、少一組狀態。** 換來的是「exit 檔一定會出現」這個更有用的保證。

代價寫在明處：**126 和 127 跟程式自己回傳這兩個碼是分不開的。** 這是選擇，不是
疏漏。

## 多筆指令

用 `aos-c` 這個程式跑一個檔案時：

- 指令**依序執行**，一次一個，不併行
- 某筆的程式回傳非零、或根本沒起來（126 / 127），都不影響後面的指令
- **某筆執行失敗也不會停止後面的指令** —— 回報之後就跳到下一筆
- 讀取失敗要看情況，見下

會跑完全部，是因為後面的指令跟失敗的那一筆沒有關係。因為一筆跑不起來就放棄剩下的，
只是把一個失敗變成一堆沒做的事。

現在會被算成「失敗」的已經很少了：找不到指令不再是失敗，只是一筆結束碼 127 的
記錄。`aos: N of M instructions failed` 這行要出現，得是 `fork`、等待、或寫 exit
檔真的出錯。

程式的結束碼：全部成功是 0，只要有任何一筆失敗就是 1，並在最後印出
`aos: N of M instructions failed`。全部成功時完全不輸出。

## 串流餵指令

`aos-c` 的來源有兩種，都是串流：

| 呼叫方式 | 來源 |
| --- | --- |
| `aos-c 路徑` | 直接開那個路徑。可以是普通檔，也可以是 **named FIFO** |
| `aos-c`（沒有參數） | 讀標準輸入，所以 `producer \| aos-c` 就是管線 |

`aos-c 路徑` 給的就是檔案／FIFO 本身的路徑，不會幫你組 `XXX/.aos/insts` 之類的
位置 —— 那是上層使用者的事。

### 消費模型：一次觸發，吃到 EOF 就收工

aos-c **無狀態、不常駐**。跑一次就是「有多少吃多少，讀到 EOF 就結束」。要它「一直
跑下去」的話，那件事外包給觸發者（cron、supervisor、或未來呼叫 ABI 的程式），不放
進 aos-c 裡面。

這樣做的好處是沒有 daemon 那一套（重開、輪詢、收工信號全免），而且解析失敗的後果從
「長命行程永久死掉」退化成「這次觸發提早結束，下次從頭再來」。

成立的前提有兩個，都在使用者這一側：

- **EOF 是生產端關閉時才會來的。** 所以生產端要是「開 → 寫一批 → 關」的批次／管線
  型程式。有人把 FIFO 開著猛灌從不關，aos-c 就會一直等下去 —— 那是對方沒有收尾，
  不是 aos-c 該防的。
- **同一條 FIFO 一次只能有一個 aos-c。** 兩個一起讀會搶記錄、各自讀到半筆而錯位。
  這裡**不**加 `flock`，它是部署紀律。

FIFO 當下沒有寫入端時，這次觸發會立刻讀到 EOF 然後結束 —— 沒事做就秒退，正是
cron 想要的行為。

### ⚠ 走標準輸入時，子行程的 stdin 會吃到指令串流

指令從 **stdin** 進來、而某筆指令**沒有指定 `stdin_path`** 的時候，子行程會繼承
aos-c 的 stdin —— 也就是那條指令串流本身。於是子行程會去吃本來要給 aos-c 的記錄。

兩個解法，都在使用者這一側：

1. 走 stdin 的話，每一筆都自己指定 `stdin_path`（要丟掉就寫 `/dev/null`）
2. 或者改用 `aos-c 路徑` —— 那條 fd 是獨立開的，而且帶 `O_CLOEXEC`，子行程的
   stdin 跟指令串流互不相干，天生沒有這個問題

所以：**串流建議優先走路徑／FIFO**，stdin 留給「每筆都自帶 `stdin_path`」或臨時
管線。

### 讀取失敗：一律停止

跟執行失敗相反，**任何解析失敗都會停止整輪**，並多印一行
`the file is not what it claims to be`。

理由是：這個格式的記錄之間沒有分隔符號，所以解析失敗幾乎必然代表某一筆多了或少了
行，而**後面每一筆都跟著位移**了。位移之後的記錄語法完全合法，只是欄位來自別筆 ——
繼續讀下去就是繼續執行沒有人寫過的指令。

而且寫入端根本產不出 `EMPTY_ARGV` 或 `TOO_MANY_ARGS`（`aos_instruction_write` 會
先擋掉），所以檔案裡出現這些，只可能來自手動編輯或損毀。

### ⚠ 錯位是偵測不到的，而且會執行你沒寫過的指令

這是這個格式最需要知道的一件事，而且**沒有任何讀取端的政策能防住**。

假設你寫了四筆，全部都是 `echo`，但第二筆不小心少了一行：

```text
echo→A     ⋯⋯八行完整⋯⋯
echo→B     ⋯⋯只有七行⋯⋯          ← 少了 extra 那一行
echo→C
  stdin = touch→/tmp/oops          ← 一個含 Tab 的路徑，完全合法
  ⋯⋯
echo→D     ⋯⋯八行完整⋯⋯
```

解析出來會是：

```text
第 0 筆：argv = [echo] [A]                      ← 對
第 1 筆：argv = [echo] [B]                      ← 「對」，但 extra 吃掉了 echo→C
第 2 筆：argv = [touch] [/tmp/oops]             ← 你從來沒寫過這一筆
結束於：INCOMPLETE
```

第 2 筆**解析完全成功，沒有任何錯誤訊息**，於是 `touch` 就被執行了。錯誤要到最後
才浮現，而且指向的位置跟真正出問題的地方（第 1 筆）不同。

為什麼防不住：每連續八行都構成一筆語法合法的記錄，`extra` 和五個路徑欄位對解析器
而言又是不透明資料 —— 沒有任何線索可以判斷「這八行是不是同一筆」。

**能做的只有兩件事：**

1. **永遠用 `aos_instruction_write` 產生指令檔**，不要手寫、不要用 shell 拼接。
   寫入端是整筆驗證完才開始寫的，不會產出行數不對的記錄。
2. **把指令檔當成不可信輸入來管**。它本來就等同於可執行程式碼（見下面的安全性
   一節），而錯位讓「內容被改動一行」的後果從「少跑一筆」放大成「跑一筆你沒寫過
   的」。檔案權限是唯一的防線。

## 狀態一覽

| 狀態 | 意思 |
| --- | --- |
| `AOS_EXEC_OK` | 有結束碼了。看 `result.status`，包括 126 / 127 那兩種 |
| `AOS_EXEC_INVALID_ARGUMENT` | argv 是空的，或第一個引數是空字串 |
| `AOS_EXEC_SPAWN_FAILED` | `fork` 失敗 —— 連子行程都不存在，沒有碼可以回報 |
| `AOS_EXEC_WAIT_FAILED` | 子行程起來了，但等它結束時出錯 |
| `AOS_EXEC_EXIT_WRITE_FAILED` | 程式跑完了，但結束狀態寫不進 exit 檔 |
| `AOS_EXEC_PLATFORM_UNSUPPORTED` | 這個平台還沒有實作行程建立 |

`SPAWN_FAILED` 和 `WAIT_FAILED` 時 `result.error` 會帶著作業系統回報的 `errno`，
可以用 `strerror()` 轉成訊息。子行程自己的失敗不走這裡，它走結束碼。

## 平台

POSIX（Linux、macOS）已經實作，用的是 `fork` / `execvp` / `dup2` / `chdir` /
`waitpid`。

Windows **還沒有**。它需要 `CreateProcess` 搭配 `STARTUPINFO` 做控制代碼重導向，
而且沒有 `fork`，所以那會是另一套實作而不是這一套的變體。在補上之前，
`aos_instruction_execute` 在 Windows 上可以編譯，但會直接回傳
`AOS_EXEC_PLATFORM_UNSUPPORTED` —— 寧可明說不支援，也不要給出會誤導的成功。

平台相關的程式碼全部關在 `src/exec.cpp` 裡面，公開標頭沒有任何平台差異。

## 安全性

**執行一個指令檔，等於用你的權限跑任意指令。**

這是這個工具的用途而不是缺陷，但意思是：**對指令檔的寫入權限等同於任意程式碼執行
權限**。如果指令檔放在別人寫得到的地方，那個人就能用你的身分做任何事。

單筆記錄有位元組預算，是為了擋住畸形檔案把記憶體吃光，但那只防資源耗盡，**不防
內容惡意**。內容的信任問題只能靠檔案權限解決。
