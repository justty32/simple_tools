Security boundary · 01

限制放錯位置，就不叫限制

Sandbox 不是判斷程式「看起來危不危險」，而是先建立一個它改不到的物理邊界，再讓它於其中執行。這和保護電路的道理相同：不能要求被保護的負載自行決定何時跳脫。

先記住唯一原則

限制必須由受信任、位於 sandbox 外的 supervisor 執行。

受限程式不能修改 policy、取得宿主憑證，或在驗證失敗時偷偷退回 unrestricted mode。

電機類比：保護元件在功率路徑之外

保險絲、斷路器、硬體 interlock 不由負載韌體控制。就算控制程式錯誤，硬體上限仍然存在。

軟體對應：host supervisor 建立邊界

supervisor 建立 container、mount、network 和 cgroup，驗證實際效果後，才啟動不可信任的 agent。

四個常見但不構成 sandbox 的東西

CWD

cwd=/workspace

只像指定程式上電後的初始位址。程式仍可用絕對路徑走到宿主使用者看得到的其他檔案。

PARSING

shell=False

避免 shell 再解讀 ;、$(...) 等字元，但成功啟動的 executable 仍繼承原 process 的檔案與網路權限。

POLICY HINT

HTTP_PROXY

這只是環境設定。若 container 仍有 default route，程式可忽略 proxy，直接連線。

OPERATION SAFETY

approval／工具白名單

很適合降低誤操作，卻不能抵抗惡意程式、被攻陷的依賴，或同 process 中能直接呼叫 OS API 的工具。

正確的心智模型

  1. 宣告
    不可變 policy
  2. 建立
    mount、net、cgroup
  3. 驗證
    允許與拒絕探針
  4. 執行
    不可信 workload
  5. 清理
    資源與證據

這條流程中，「產生了正確設定」不等於「限制真的生效」。如同控制系統不只看 command，也要量測 effective output；啟動前必須從 container 內實測允許路徑可用、拒絕路徑不可用、沒有旁路網路。

先分清兩種限制

APPLICATION

邏輯預算

Round、token、tool-call 次數、可用模型。由 agentloop 看得到並計數，避免成本或迴圈失控。

OPERATING SYSTEM

存取與資源邊界

可見檔案、網路路徑、process identity、CPU、RAM、PID、capability。必須由 OS/runtime enforcement。

兩者互補，不可互相冒充。 Tool-call 上限不能阻止一個已獲准的 shell command 讀取整個 home；container 也不會自動理解 LLM token 預算。

信任邊界圖

受信任 host
┌──────────────────────────────────────┐
│ supervisor：policy、生命週期、驗證   │
│ secret broker：保存長效 credential   │
└──────────────────┬───────────────────┘
                   │ 狹窄 IPC / session token
                   ▼
┌──────────────────────────────────────┐
│ 不可信 agent container               │
│ 只見獲准 mount · 無直接外網 · 有上限 │
└──────────────────────────────────────┘

「不可信任」不是說 agent 一定惡意，而是架構不依賴它永遠正確。這與 fail-safe 設計相同。
