C++ 固化，不是把 Python 翻成 C++

若你熟悉韌體、驅動或 Go service，可以把「固化」理解成：把已量測、已定義的控制律，從方便試驗的 bench 搬進可長期驗證的 controller。真正要選的是責任邊界，不是語言勝負。

先看訊號怎麼流

Python oracle探索與量測
JSON / events凍結外部契約
C++ core算下一狀態
typed intent交給 adapter
Linux執行與強制

這是責任流，不一定是五個 process。重點是 core 不在 getter 裡偷做 HTTP、spawn 或改檔。

把術語翻成工程語言

Reducer／狀態轉移

類似離散狀態機：state + event -> new state + intents。輸出 effect 請求，但不親自碰硬體或網路。

Invariant／永遠要成立的約束

像電流、能量或 buffer ownership 的守恆條件；例如 child 權限不能比 parent 大、budget 不能重複退款。

Adapter／帶副作用的驅動層

把 typed intent 轉成 HTTP、SQLite、process、cgroup 或 FUSE 操作，再回報 result event。

TCB／可信計算基底

出錯就可能破壞安全承諾的全集。C++ binary、parser、adapter、設定與 kernel 都可能在內；native 不等於安全。

Differential oracle

同一批 golden vectors 同時餵 Python 與 C++，比較 normalized output、transition、error kind，而不是只測兩邊都「能跑」。

C ABI／邊界格式

跨 compiler 或語言只露 opaque handle、bytes 與明確 allocator；不讓 STL、exception、物件 lifetime 穿越邊界。

什麼該搬，什麼先別搬

問題傾向 C++ core留在 Python／adapter
契約versioned schema、path、ledger、Round state 已穩定message shape 或 provider quirks 還在探索
工作型態純決策、高頻 event、需嵌入或低 idle RSSLLM／外部工具等待主導，搬語言不會變快
能力可用 fixtures 重播，ownership 與 cancel 已寫清楚依賴 Python reflection、任意 callable 或 SDK 隱藏行為
風險sanitizer、fuzz、雙 compiler CI 可長期維護UB、ABI、thread race 會讓 TCB 反而變大

為何第一刀是 tooljson

它像一塊可單獨上測試台的數位模組。輸入是 versioned JSON，輸出是 validation、argv/stdin decision 或 typed error；不必先處理 TLS、SSE、模型延遲與 sandbox。先做 15–20 個 vectors，讓 C++ 只讀 fixture、不跑 production effect，再 shadow、opt-in、成為 default。

若這一刀連 canonical output、unknown-field policy、Linux/Windows pure-core gate 與 parser fuzz 都守不住，就應停止擴張，而不是用更多 framework 掩蓋契約空白。
