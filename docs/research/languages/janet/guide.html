Janet · data + reduction · typed effects

Janet 固化，是把規則做成一台小型語意機器

對熟悉 C++、Go 或 Lua 的人，Janet 的價值不是括號或 REPL，而是用很小的資料模型表達狀態、規則與組合。它適合控制面；TLS、process、container 與 mount 仍交給有實證的 adapter 和 Linux。

核心像離散時間控制器

State + Event可序列化輸入
→
Janet reducer純規則與不變條件
→
State + Intent交給 effect adapter

adapter 的 result 再成為下一個 event。如此可以 replay、差分測試，也能在不碰真模型或真 process 時驗證控制邏輯。

跨領域術語對照

Semantic core

像協定狀態機加 policy engine：擁有 path、permission、Round、ledger、context manifest 的決策，不擁有外部世界。

Reduction

state + event -> state + intents。不是任意求值；同一輸入應產生可比較的 transition。

Environment / namespace

類似每個 task 的 symbol table 加可見資源表；決定看得到什麼，但「看得到路徑」不代表已授權。

Binding / handle

handle 是解析後且帶 authority 的 reference，應綁 actor、instance、grant generation；不是一條可猜的名稱。

Quote / checked dereference

memory 內容先當 data；load 時重驗 ACL、depth 與 budget。文字長得像指令，也不會自動升權。

Intent / effect

Janet 只提「要 spawn」的 typed request；supervisor 依 policy 重建 argv、mount、network，再執行 OS effect。

類比不是 enforcement。Plan 9 path、Lisp environment 與 capability binding 能讓設計更清楚，但不能取代 kernel 隔離；Janet core 小，也不代表 supervisor、adapter 與設定不在 TCB。

為何不直接全面 Janet 化

「API 存在」不等於「production backend 已證明」。現有實證支援 JSON、fake HTTP/tool loop、fiber/channel 與 CLI；反證則包括 HTTP 無 TLS/SSE、Windows subprocess access violation，以及 FUSE/9P、cgroup 尚未落地。因此合理結論是：語意核心很合適，effect backend 逐項驗證。

第一刀仍是 tooljson：用共同 fixtures 驗 parser、strict validation、registry 與 argv decision。先讓 Janet 當 CLI shadow，差異分類為 Python bug、Janet bug、規格空白或平台差異；不要只改 fixture 求綠燈。

決策快速檢查

  • 外部行為能否完整表示成 JSON、bytes、argv 與 event trace？
  • pure decision 是否已與 filesystem、network、process effect 分離？
  • 是否有正常、錯誤、重播、crash/retry fixtures，而非只連真模型？
  • 若 adapter 失敗，idempotency、deadline、cancel 與 fail-closed 是否有明文語意？
