RESPONSIBILITY · OWNERSHIP · EFFECT

每一層只承諾自己的事

好架構的重點不是名詞多，而是誰擁有狀態、誰能產生副作用、掛掉後留下什麼，都能直接回答。

1. agentloop：原始本地核心

loop

run() 連續跑 Round；advance() 一次跑 Step 或 tool batch。模型與工具仍在呼叫者 process 執行。

Handle + Limits

Handle 是公開可變狀態與合作式控制；Limits 在 callback boundary 檢查步數、工具與 token，不限制 CPU、RAM 或網路。

2. Controller：第一個方便 wrapper

Controller 像「C with class」：組合 bot、初始輸入、Handle 和 runner 樣板。它可演進，其他人也能直接在 Handle 上做不同 abstraction。它不保證 ACL、database、revision、scheduler 或 sandbox。

c = agentloop.Controller(bot, dispatch, "開始")
c.start()
c.pause()
with c.handle.edit(): c.handle.prompt = "再檢查一次"
c.resume()
result = c.join()

3. 互動入口與 control adapters

入口角色不擁有什麼

GUI／vim 式 UI廣義 shell不應藏真實狀態

把它們想成未來 agent world 的基礎 library 是合理的，但 endpoint 有成本、延遲與不確定性；工具有權限與副作用。schema 驗證、approval、資源上限和 OS sandbox 是不同邊界。

5. 外圍 Agent Machine（現在起步）

若 process 重啟後還要找回工作，就不能保存活的 Handle、callback 或 callable；應保存可序列化 operation、已提交結果與 effect 狀態。worker 取得短暫 lease，transaction 發布完整 generation，防止舊回報覆蓋新狀態。

這些仍不是 Controller API。 第一個 Python PR 只做 path、immutable snapshot、root generation 與 pure tests；durable store 和 scheduler 分階段加入。

6. runtime security 是正交邊界

permission、filesystem/network visibility、CPU/RAM/PID 上限與強制終止需靠獨立 process、OS、container 或 VM。durable store 能恢復狀態，但不能隔離 hostile code；sandbox 能限制 process，卻不會判斷 Goal 是否達成。

7. 為何未知副作用不能 retry

寄信、付款、部署可能已成功，只是回覆在 crash 時遺失。這種 unknown effect 要以 operation id 查詢、reconcile 或交給人；自動再跑可能重複副作用。模型 request、純讀取與不可逆工具需要不同 retry policy。
