# 還沒做的

按「做了之後解鎖多少東西」排。每一項都寫了**為什麼還沒做**與**怎麼做**，
不是願望清單。

---

## 已完成（原本在這裡的三項）

- **逾時**（`ExecOptions::timeout`／`grace`）
- **輸出上限**（`ExecOptions::max_output_bytes`）
- **收工等工作走完**（`src/tracker.hpp` 的 `WorkTracker`）

細節見 README〈逾時與輸出上限〉與〈收工〉。三項都保留了同一個分工：
**機制在核心，政策在各條 loop**。

---

## 1. 監看目錄

**狀態**：stdin 與 socket 都做完了；監看目錄那條還沒。

**已定的決定**：socket 走「**收下就回**」——`{"ok":true}` 只代表排進去了，
client 自己輪詢 exit 檔。所以 loop 的形狀完全沒動。

監看目錄那條同理，而且更簡單（本來就沒有連線要回應）：掃一個 spool 目錄，
每個 `.json` 檔是一個請求，收下就搬走。

⚠ 要想清楚的是**搬走的時機**：先搬再 dispatch 的話，中間崩潰請求就消失了；
先 dispatch 再搬的話，重啟會重送。跟 agent 那條「先存進度再派工」是同一類問題，
答案多半也一樣：**寧可停住，不要重複**。

---

## 2. `Unknown` 之後怎麼辦

**狀態**：完全沒有政策。`Unknown` 代表「不知道做到哪了」，所以**不能自動重跑**——
但也不能就這樣放著。

要設計的是：誰來看、看什麼、人介入的介面長什麼樣。
`ext/agent` 目前是把它丟給 `Controller` 決定，那只是把問題往上推了一層。

---

## 3. 搶佔

**狀態**：優先權只影響**還排在 queue 裡**的東西。已經在跑的不會讓位，
所以一個低優先權的長工作還是會佔住一條 worker。

要搶佔就得能砍掉跑到一半的工作——逾時那條路已經有 `kill_group` 了，
機制在；缺的是政策（誰可以搶誰、被搶掉的算什麼結論）。

---

## 4. Task tree

**狀態**：`ext/agent` 只有一層 Round → child。child 自己再開 children
（`agent-machine` 文件講的 Task tree）還沒做。

⚠ 做之前先想：現在「一個 Call 的 exit 檔只有一個人寫」是靠**路徑各自獨立**保證的。
多層之後要有一套路徑配置規則，不能靠每個人自己小心。

---

## 已經做完、但值得記著的限制

- **沒有 Task ID**。`agent-machine` 說 ID 在 durable accept 時配置，
  這裡還沒有 admission 那一層。
- **env 只帶得走環境變數**。`ulimit`／`umask`／fd 設定帶不過去，
  原因見 README 的〈env 檔〉——那是為了保住 `LaunchError` 的區分而做的取捨。
- **exit 檔只有一個數字**，所以 `exit 137` 和 `SIGKILL` 在檔案裡分不開。
  完整的區分在回傳的 `Outcome` 裡（逾時／爆量則有自己的 124／123）。
- **逾時的輪詢最快 1ms、退到 20ms**，所以砍掉的時刻會比設定值晚一點點。
  要更準就得換成 `pidfd` ＋ `poll`（Linux 專屬）。
