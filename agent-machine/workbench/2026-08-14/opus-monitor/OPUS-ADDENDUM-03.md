# OPUS-ADDENDUM-03：忙碌、排隊與 active Tasks

## 1. 結論與對 Round 03 的修正

**撤回**「普通外來 Call 預設排隊」。新方向更好，理由不是它由使用者決定：我自己在 `OPUS-REVIEW-03` 反例 4 就寫過「預設排隊會讓一個壞掉的長工作把後面全卡住」，而「預設拒絕、不建 Task」直接消滅了它——隊列只在明確要求時才存在。

真正的修正是把我原本混成一件事的東西拆開：**准入**（建 Task 前就拒絕，零 Task）與**排隊**（Task 已存在但無執行資格）。tree lease 保留，但縮小成「寫入資格」，不再是預設等待的對象。

最重要的新發現：必須明確把 **parent 呼叫 child 排除在准入檢查之外**，否則 composite Function 會被自己所在的 root 判定為「正在忙」而把自己擋死。

## 2. 使用者決定與我的候選

**使用者已定（不重議）**：`REQUEST-03A` 第 1–5 點，全數照收，本文不再重述。

**仍是我的候選**：寫入資格的範圍與名稱、child 繼承、唯讀是否並行、投影的通知方式、兩道 gate 的先後、原型順序。「寫入資格、收件區、投影、active set」都是示意名稱，不是規格。

## 3. 修訂後的 tree lease

推薦：**保留，但縮小成「寫入資格」，並和排隊脫鉤**。它只剩三個職責：准入判定的依據（純讀）、資格的授予對象（一棵 tree 而非單一 Task）、進階並行下的發布點保護。

四條路徑必須分開，不可混成同一種 queue：

```text
普通外來呼叫   -> root 忙 -> 拒絕，零 Task、零目錄
明確追加       -> 不建 Task、不取資格 -> 進 AOS 管理的收件區
明確排隊 Task  -> 建 Task -> 無執行資格 -> 每次嘗試都過兩道 gate
parent -> child -> 繼承 parent 的資格 -> 不經准入
```

**追加為什麼不會變成第二棵 tree**：它不碰 agent 記憶，只寫 AOS 管理的收件區，目前 Task 在下一個邊界自己去取。反例（若追加直接寫記憶）：agent 正在 Step 中途改寫 `memory/notes.md`，追加也寫 `memory/`，地盤立刻兩個寫入者。

**死鎖**：child 必須繼承資格。反例：

```sh
aos exec ./ask "整理筆記"        # T1 取得寫入資格
# T1 呼叫 ./ask/functions/apply
# child 若走普通呼叫 -> AOS 回「正在忙」-> T1 把自己擋死
```

**會推翻這個推薦的反例**：使用者第 5 點已經預期「同一 root 兩個 active Tasks」。若把寫入資格定義成「唯一的 active Task」，這種情況就無法表達，投影也沒東西可顯示。最小修正：**active 數與資格數是兩個量**——資格是 0 或 1，active 可以大於 1（唯讀計算或隔離工作區）。「lease = 唯一 active」這個等式必須拆掉。

## 4. 三套並行方案

| 方案 | 讀 | 計算 | root 寫入 | 外部作用 |
|---|---|---|---|---|
| 完全序列化 | 並行（讀已發布） | 並行 | 僅資格持有者 | 僅資格持有者 |
| 受限並行（單一發布者） | 並行 | 並行 | 僅發布者 | **不受保護** |
| 隔離工作區 | 並行 | 並行 | 發布時序列化 | **不受保護** |

| 方案 | 優點 | 代價 | 失敗反例 | 階段 |
|---|---|---|---|---|
| 完全序列化 | 規則最少、恢復單純 | 長工作期間什麼都不能改 | 排隊 Task 條件早已成立，卻因前一個 Task 等人回覆而無法開始 | 第一版 |
| 受限並行 | 長計算不阻塞 | 要能區分「算完未發布」，衝突時整份丟棄 | 兩個 Task 都讀 M0，前者發布 M1，後者已過期，必須停住且不可自動合併 | 序列化穩定後 |
| 隔離工作區 | 可平行試多方案 | 磁碟、清理、衝突；看到的路徑不是真 root | 私人工作區寄了信，工作區被丟棄但信已寄出 | 需要平行探索時 |

受限並行建議採**單一發布者**而非預先分開寫入區：分區要事先知道每個 Task 會碰哪些路徑，agent 的工作通常無法預先宣告。

三案共通：**外部作用不會因丟棄工作區或放棄發布而回滾**，只有「intent → 執行 → Receipt」加上「結果不明不自動重送」能處理它。

第一個 Python 原型做**完全序列化**：它已是主線預設，也是另外兩案的基準線，沒有它就量不出並行的收益。

## 5. 中央真相 → 投影 → agent 知情

方向與順序固定：

```text
中央 commit 授權 -> 落盤 -> 原子替換投影 -> 才允許 Task 開始執行
```

- **投影最晚何時可見**：授予資格之後、Task 真正開始之前。反過來的話，agent 一開始就會讀到沒有自己的投影。
- **active set 改變時最晚何時知道**：下一個 Step／Round 邊界之前。

三種通知做法：**邊界重讀**最簡單且天然對齊決策點，代價是邊界之間不知情；**AOS 主動送事件**即時，但要通道與送達保證，收不到仍得退回重讀；**agent 自行查詢**最靈活也最容易忘。原型選邊界重讀。「只寫檔不等於已通知」的解法是把義務放在 agent 端：保證它在下一個邊界一定重讀。

三條 fail-closed 規則：投影必須帶中央狀態世代與這次 AOS 啟動的識別，不符即過期；投影缺失、半寫或過期的語意是「**不知道**」，不是「沒有其他 active Task」；投影**永不授權**，資格只能來自中央。

反例 A（中央已改、投影未更新就 crash）：

```text
中央：T2 已取得寫入資格（已 commit）
AOS 在寫投影前 crash
重啟：投影仍寫著只有 T1
```

若 agent 相信投影，就會以為自己是唯一寫入者。修正：重啟必須**先重建投影再恢復執行**，舊啟動識別的投影不採信。

反例 B（重建期間短暫歸零）：

```text
重建投影：先清空、再逐一寫入
執行中的 agent 剛好在空檔重讀 -> active = 0 -> 以為自己獨佔
```

修正：投影只能**整份原子替換**（寫暫存名再改名），不可原地清空重填；配合第二條，讀到缺失也只會得到「不知道」。

## 6. 兩道 gate

```text
便宜預篩：條件 gate（純讀）
 -> 取中央鎖
 -> 同一持鎖區間內重驗：條件 gate + root 安全 gate
 -> commit 授權 -> 落盤 -> 原子換投影 -> 開始執行
```

先條件後安全，因為條件純讀、便宜、常常不成立，適合先過濾。但**做決定的那一次，兩道必須在同一持鎖判定點同時成立**，否則會有「鎖外成立、取到鎖時已不成立」的空窗。

**crash 後為何必須重驗**：授權是持久事實，「條件仍成立」與「root 仍安全」都不是。授權未 commit → 全部重來，因為停機期間條件可能變了。授權已 commit 且投影已更新 → Task 已在執行，走既有的結果不明判定，不重跑 gate。

**任一關不成立**要分兩種：

- **不成立 → 繼續等待**：條件還沒到、別人正持有資格，都是暫時的。
- **無法判定 → 停住請人處理**：條件引用的東西已不存在，或中央與投影不一致到無法判斷 root 是否安全。不要猜。

root capacity 不是固定數字，而是一次判定：序列化問「有沒有人持資格」，受限並行問「發布者是否空著」，隔離工作區問「能否再開一個工作區」。

## 7. 最小 Python 原型（4 步）

1. **准入與排隊分家**：普通呼叫在建 Task 前被拒，零 Task、零目錄；明確排隊建 Task 但無資格。→ 決定兩條路徑是否真的分離、「零 Task」是否可驗證。
2. **child 不經准入**：parent 持資格時 child 繼承，同時驗外來普通呼叫仍被拒。→ 決定 child 繼承是否足以避免自我擋死。
3. **投影原子替換 + 邊界重讀**：授權後、換投影前殺掉 AOS，重啟必須先重建投影；驗 agent 在邊界讀到「不知道」而非「零」。→ 決定投影方向與 fail-closed 語意。
4. **兩道 gate 同一判定點**：預篩後取鎖重驗，在授權 commit 前後各殺一次；驗「不成立→等」與「無法判定→停」。→ 決定 gate 先後與 crash 重驗規則。
