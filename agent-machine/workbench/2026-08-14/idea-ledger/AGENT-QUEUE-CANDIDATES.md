# Agent 忙碌時的候選細節

> 本頁只整理尚待原型的細節。預設拒絕、明確追加與明確排隊，已由使用者決定。

## 三條操作不能混在一起

```text
普通新呼叫
  -> agent 忙碌：直接拒絕並告知
  -> 不建立 Task，也不偷偷保存成排隊工作

明確追加 prompt
  -> 加入目前 Task
  -> 不建立另一個 Task
  -> 等安全邊界才讓目前 Task 看見

明確建立排隊工作
  -> 建立新的 Task
  -> 保存「目前 Task 到了什麼狀況才可執行」
```

這樣可讓使用者從 Task 數量看出真實情況：被拒絕就是沒有收下；追加仍屬於目前工作；排隊才會多一個 Task ID。

操作名稱與正式命令尚未決定，本頁不先發明 CLI。

## 追加 prompt：何時生效

### 方案 A：下一個 Step 邊界

目前 Step 做完並保存結果後，再把 prompt 交給目前 Task；下一個 Step 規劃時可以看到。

優點：最符合「Step 是原子操作邊界」的方向；不會在 Tool 已執行一半時改變意思。

缺點：長時間 Step 會讓新訊息等很久；若 Step 卡住，prompt 也不會生效。

建議：第一個原型先試這案。

### 方案 B：Round 結束才生效

整個 Round 完成後才讀取追加 prompt，並開始下一個 Round。

優點：一個 Round 的上下文最穩定，容易重現與說明。

缺點：回應慢；目前 Round 若含很多 Steps，新需求可能很晚才被看見。

### 方案 C：只有暫停或等待使用者時生效

Task 到達明確的 paused／waiting 邊界才接收追加內容。

優點：最不容易干擾正在做的事。

缺點：有些 Task 不會自然到達這種狀態；「我現在就想補一句」的體驗較差。

### 不建議的第一版：Step 中途注入

LLM 或 Tool 正在執行時立即改動它看到的 messages，會讓 Step 的輸入不固定，也很難在 crash 後重現。若未來需要中斷，應設計成明確取消目前 Step，再用新輸入建立下一個 Step。

## 排隊 Task：開始條件候選

排隊不是只有一個先後號碼。新 Task 至少要保存它依賴哪個目前 Task，以及開始條件。

可先比較這些條件：

| 條件 | 白話意思 | 主要風險 |
|---|---|---|
| 目前 Task 正常完成後 | 前一件成功才開始 | 需先定義 composite Function 的成功 |
| 目前 Task 結束後 | 成功或已知失敗都可開始 | 後一件可能建立在失敗結果上 |
| 目前 Task 安全暫停後 | 前一件未完成也可交棒 | 必須明確釋放 agent root 寫入權 |
| 使用者明確放行後 | 到時再由人決定 | 需要人工介入，不能全自動 |

條件名稱、可否組合，以及取消前一件時如何處理後續，仍待原型。第一版可只支援一兩個清楚條件，不急著做完整條件語言。

## 前一個 Task 結果不明

若目前 Task 可能已造成外部作用，但缺少完整結果，AOS 不能把它當成功或普通失敗。

候選處理：

1. **停止後續並請使用者處理**：最安全，建議第一版採用。
2. **取消依賴它的排隊 Task**：簡單，但可能丟掉仍有價值的工作。
3. **條件明確允許結果不明時仍執行**：彈性最高，也最容易重複外部作用；只適合使用者清楚承擔風險時。

無論選哪案，都不能把「結果不明」偷偷解讀成「前一件沒做，所以放心開始下一件」。

## 同一地盤若同時有多個 Task

條件判定為可執行，不代表同一 agent root 就適合多一個寫入者。排程前還要確認它會不會和現有 Task 同時改同一批檔案。

使用者已要求：若同一 root 同時有兩個 Task 在執行，地盤內要能看見 active Tasks，而且這份資訊由 AOS 管理。這是「讓 agent 知情」的最低要求，不等於已允許兩個可寫 Task。

可比較三種做法：

### 方案 A：同一 root 仍只有一棵可寫 Task 樹

新 Task 即使開始條件已滿足，仍要等寫入權釋放。地盤內的 active 清單可同時顯示一個 writer 與其他唯讀／等待工作。

優點：最不容易互相覆蓋；符合先前避免多個自我修改實例的偏好。

缺點：長工作仍會阻塞後面的寫入工作。

### 方案 B：共用 live root，允許多個 writers

所有 active Tasks 都能看到彼此，但仍直接修改同一目錄。

優點：並行度最高，實作看似直接。

缺點：看得見不代表不衝突；兩邊仍可能讀舊資料、覆蓋檔案或同時修改 Definition。只有 active 清單不足以讓這案安全。

建議：第一版不要採用，除非另有可靠的版本檢查與寫入衝突測試。

### 方案 C：每個 Task 有私有工作區

Root 內可看見多個 active Tasks，但各自在隔離目錄修改；最後發布時比較 base version。

優點：能平行探索，檔案不會在執行中直接混在一起。

缺點：發布、衝突、清理與外部作用都更複雜；active 清單還要說明每個 Task 的 workspace。

建議：留給後期原型。

## Active Tasks 如何在地盤內可見

尚可比較：

- AOS 在 machine-local `.aos` 區域發布唯讀狀態檔或目錄。
- `./task list` 代理從中央 AOS 讀取，但在 agent root 內提供固定入口。
- 兩者並存：檔案供 agent 讀，命令供人操作；必須明定哪邊是唯一真相。

檔名、JSON 格式與正式權威尚未決定。無論採哪案，都應：

- 由 AOS 更新，不讓 Task 自己宣稱 active。
- 與可攜 memory／Definition version 分開，避免狀態變動讓 Function 看似換版。
- AOS crash 後先標示資訊可能過期，完成 recovery 才重新發布。
- 不把 PID、fd 或 worker claim 當成可進 Git 的 Task 身分。

## 保存位置候選

- 追加 prompt 應先成為目前 Task 的已落盤輸入記錄，到安全邊界才被消費。
- 排隊 Task 有自己的 Call、Task ID 與開始條件；不能只放在記憶體 queue。
- busy 回覆不建立上述任何記錄，只能留下非 Task 的操作日誌；是否保留這種日誌仍可選。
- machine-local worker／claim 不進 agent repo；可攜 checkpoint 是否包含尚未執行的排隊 Task，留給持久化原型決定。

## 尚待原型

- agent 忙碌時做普通呼叫，Task 數量是否完全不變，回覆是否明說「未收下」。
- 追加 prompt 後是否沒有新 Task ID，且只在選定邊界出現在目前 Task。
- crash 發生在「追加已落盤、尚未被 Step 讀取」時，重啟後是否只消費一次。
- 建立排隊 Task 時缺少條件，是否直接拒絕而不是套隱藏預設。
- 前一 Task 成功、已知失敗、取消、暫停、結果不明時，各條件是否只有一種可預測結果。
- 兩個 writers 同時修改同名檔案時，方案 B 是否能可靠阻止覆蓋；不能就維持單 writer。
- active 狀態發布前後殺掉 AOS，地盤內是否不會把舊 Task 長期顯示成 active。
- clone／attach 後排隊 Task 是否保持 paused，不因換機自動執行。
