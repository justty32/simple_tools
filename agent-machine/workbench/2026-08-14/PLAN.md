# 2026-08-14 回合制工作計畫

地位：今日協作紀錄，不是 AOS 規格。主 agent 負責排程、裁決與正式文件；其他 agent 只能在被分配的範圍工作。

## 角色

| 角色 | 模型 | 工作 | 可寫範圍 |
|---|---|---|---|
| 主 agent | Sol | 排程、整合、裁決、正式稿 | 全部；避免覆蓋使用者檔案 |
| 核心設計 | Sol | Function／Step／Task 與反例 | 第一輪只讀；原型另分目錄 |
| Runtime 設計 | Sol | Linux、C++、排程、恢復 | 第一輪只讀；原型另分目錄 |
| 使用體驗 | Sol | `.aos/`、CLI、agent 上層 | 第一輪只讀；原型另分目錄 |
| 文檔員 | Sol | 將裁決寫成完整稿與精簡稿 | 一次持有一組指定文檔 |
| 實作／審查 | Terra | 小型原型、code review、測試設計 | 每次指定一個獨立目錄 |
| 機械驗證 | Luna | 測試矩陣、尺寸、連結、重複掃描 | 原則上只讀或輸出到獨立目錄 |

## 回合

### 第 1 回合：各自提出方案

三位 Sol 不看彼此答案，分別回答：最小可行核心是什麼、哪裡可能錯、要做什麼原型才能推翻自己的設計。

輸出：三份提案。禁止改正式文件。

### 第 2 回合：交叉找碴

每位設計者閱讀另外兩案，只找：定義衝突、不可恢復情境、使用上令人困惑之處、過早引入的複雜度。

輸出：反例清單。主 agent 將結果收成「已定、暫選、延後、淘汰」四欄。

### 原型 0：一個 Function

只驗證一件事：不經 shell 啟動一個程式，完整保存 argv、stdin、stdout、stderr 與結束原因。

先用 Python 快速試錯，再由 C++ 跑同一組測試向量。通過後才討論 Step；失敗就先修正 Function 定義。

### 原型 1：一個 Step 與收據

加入提交前落盤、唯一 attempt、結果收據、重啟與「結果不明」。比較普通檔案+journal 與 SQLite 的實作／檢查成本。

Python 先驗狀態轉移；C++ 再驗型別與持久化接縫。Janet 只可讀不可修改的候選資料，回傳排序或下一步建議。

### 原型 2：線性 Task 與 `.aos/`

兩個 Steps 依序執行，加入具名 queue、pause 邊界與 `.aos/`。由不同 agent 實際操作，記錄第一次使用時的疑問。

另做一個 C++ 內嵌 Janet 的小實驗：Janet 選候選，C++ 重新驗證並提交。若 Janet 能繞過 C++ 直接改正式狀態，該介面即判定失敗。

### 第 3 回合：從原型反推設計

每個原型都要回答：哪些規則有證據、哪些只是好聽、哪些命名讓人誤會、下一層是否真的必要。

### 收斂

先寫 `full/` 的完整、自洽版本；再抽成根層短文與 HTML。未採用方案移入 `archived/`，不得留在正式閱讀路徑。

## 三語言原型規則

```text
Python  快速建立模型、故障案例與可讀操作介面
C++     固化 process、bytes、狀態型別、持久化與 manager 權威
Janet   表達可替換 policy；輸入快照、輸出決策，不直接做正式提交
```

三者共用版本化 fixtures，不以「看起來差不多」判定相容。Windows 可以先驗資料與嵌入；`execve`、signal、Unix socket、`flock`、`fsync` 等 Linux 契約必須在真正 Linux 環境另跑，不能用 Windows 結果代替。

## 使用者審閱規則

- 任務放 `wait_user/`，每項 2–5 分鐘。
- 每項只問一個問題，附推薦預設與「不回覆會怎麼做」。
- 不要求先讀完整規格；先給命令、畫面或一頁短手冊。
- 回饋只需一句直覺，不要求使用正式名詞。
- 使用者忙碌時，所有非關鍵選擇由主 agent暫選並繼續；真正會改變 AOS 核心的選擇才保留待確認標記。

## 修訂單與交棒

1. 使用者的新意見先由主 agent 記成一張短修訂單。
2. 設計 agent 可提供影響分析，但不直接散改文件。
3. 主 agent 決定「接受、試驗、延後或拒絕」。
4. 文檔員一次收到一批已裁決修訂，並成為那些檔案的唯一寫入者。
5. 文檔員交棒後，Luna 做只讀一致性檢查；問題回到原文檔員修正。
6. 主 agent 只在最後做抽查與正式區提升，不和文檔員並行寫同一檔。
