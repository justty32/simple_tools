# Function 的資料夾入口

Function 可以由檔案或資料夾承載，這是**使用者已定**的方向；資料夾內要用哪個入口、怎麼界定 Definition（工作定義）範圍，仍是**尚未決定**。本頁比較入口，不把「整理成資料夾」誤當成 composite Function 或 child Task。

## 先守住的邊界

- 一個單檔長成資料夾，若仍只做一件 leaf 工作，AOS 看到的仍是一個 Function、一次 Task；只有需要獨立結果、pause、外部作用或重用邊界時，才明確呼叫 child Function。
- AOS 應使用呼叫者指定的 target，不猜 `main.py`、`run` 或任一剛好可執行的 helper。
- 入口、helper、prompt 與設定哪些算 Definition，以及預設 `cwd`，都沒有正式算法。已接受的工作也不可在 dispatch 時悄悄換用新版入口。

## 方案 A：固定 `call` 檔

資料夾只認 `call` 為入口，例如 `ask/call`。優點是最小、容易閱讀，檔案型 `ask` 變成資料夾型 `ask/` 時也有機會保留外部呼叫外觀。缺點是入口以外的型別、版本與依賴範圍沒有地方明說，日後仍要補機制。

**目前推薦：**先在小原型採此案，驗證 file→directory 後 argv、stdin、stdout、stderr、exit 與 `cwd` 是否仍可說清楚。

**推翻條件：**若最小原型已需要多個受支持入口、可驗證的依賴清單，或固定名稱無法避免錯跑 helper，就改比較方案 B，而非加猜測規則。

## 方案 B：manifest 指定入口

資料夾放一份入口設定檔，明列實際入口、必要 Definition inputs 與可能的型別資訊。優點是日後可檢查「這次到底用哪些檔案定義工作」，也能拒絕雙入口或缺入口。缺點是設定檔與實檔可能不同步，解析、版本與錯誤處理都會增加。

**目前推薦：**把它列為固定 `call` 之後的主要比較對象，不先決定檔名、格式或欄位。

**推翻條件：**如果單一固定入口加一份小型明列清單已滿足版本與維護需求，manifest 的解析成本沒有帶來可驗證好處，就不要提早引入。

## 方案 C：薄 launcher 加模組目錄

保留原本的 executable 檔作很薄的轉接，再把內容搬到相鄰 module 目錄。優點是 shell 使用者仍可直接面對原檔，舊程式可逐步搬移。缺點是一個 Function 有兩條 path，Git 移動、Definition 身分與相對路徑都較難解釋。

**目前推薦：**只用於相容性遷移實驗，不作預設形狀。

**推翻條件：**若真實既有工具無法安全由檔案搬成目錄、而薄轉接能保留已驗行為，可在明確範圍內採用；若新 Function 不需要相容舊 path，應避免雙路徑。

## 方案 D：獨立的 `.aos` 描述檔

以與工作內容相鄰的 AOS 描述檔指向資料夾入口。優點是 Function 身分一眼可辨，日後可承載較多資訊。缺點是又多一條身分路徑，且可能破壞使用者偏好的自然 shell 外觀；`.aos` 本身的形狀也尚未裁決。

**目前推薦：**明確延後，不讓入口需求提前決定 `.aos` 布局。

**推翻條件：**只有在跨多種 Function 類型時，固定入口與 manifest 都無法讓人清楚辨認、驗證與搬移，才值得做獨立描述檔原型。

## 下一個小驗證

把一個單檔 leaf 逐步改成資料夾入口，並刻意放入假的 `main.py` 與 `run`；驗證 AOS 仍只選正式入口、缺入口在任何外部作用前停止，且單純整理不多出 child Task。詳細背景見[Function 成長候選](../../workbench/2026-08-14/idea-ledger/MODULE-EVOLUTION-CANDIDATES.md)。
